# Installed source-native mathematics through the existing SDK manifest spine

Existing owners: central mathematical integration `StegVerse-Labs/.github#2615`; SDK application spine `StegVerse-org/StegVerse-SDK#61`. This is a **source-only generic compatibility candidate**, not a new Goal Task, SDK governance engine, standalone executor or resident runtime.

The published `stegverse.route.source-native-math.v1` binds `native_source_math` to the existing `stegverse run-manifest` dispatcher and its unchanged pre-enrichment result-lineage hashes. An application owner installs an independently authorized source distribution with an entry point in `stegverse.native_math.v1`; the SDK never fetches private code, never imports caller-chosen modules and never treats a route ID as permission. Without exactly one installed matching distribution/version/entry point, fail closed. Before invocation the exact on-disk original native source file must match the pinned Git blob SHA-1, and the actual frozen original specimen bytes must match the native input's SHA-256. A declared source commit is **not attested** by the caller-supplied label. The owner/distributor must separately prove installation provenance, license/redistribution rights, Git commit-to-blob correspondence and sandbox policy. The SDK does not silently infer any of them. The SDK executes only operator-installed source packages in its existing process; this route declares `sandbox_required=false` because **run-manifest supplies no independent OS sandbox**. An untrusted source package must be isolated or declined by its existing installation owner before use. This flag is not approval to run arbitrary untrusted code.

Source packages implement `evaluate(document, original_specimen_bytes=actual_bytes)` and return an object with a native `result_sha256` equal to SHA-256 over the canonical sorted compact UTF-8 JSON object *excluding* that field. The SDK verifies and preserves the unmodified original result, optionally checks the frozen known-case expected digest, and wraps it with pinned local source blob and specimen hashes. Its existing dispatcher separately hashes the canonical manifest, resolved route, dispatch request and the original processor envelope **before SDK lineage enrichment**. Native source result hashes and SDK processor-result hashes are different claims.
